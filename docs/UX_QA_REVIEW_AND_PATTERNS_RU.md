# UX / QA Review + Daily Report Patterns

## Что нашлось по текущему интерфейсу

### 1. Перегруз текста

- экран содержал слишком длинные описания и повторяющиеся объяснения;
- важные действия терялись внутри декоративных блоков;
- onboarding занимал слишком много внимания.

### 2. Плохая работа с длинными заметками

- сырые заметки попадали в preview почти как есть;
- длинный блок текста превращался в нечитаемую простыню;
- внутри Telegram это особенно больно из-за узкой ширины Mini App.

### 3. Нет отдельного copy-ready формата

- HTML-preview удобен для чтения внутри приложения;
- но для пересылки и вставки в Telegram/почту/Confluence нужен plain text;
- без этого пользователь вынужден вручную копировать из неидеального представления.

### 4. Риск переполнения Telegram

- большие отчёты могут быть длиннее лимита одного сообщения;
- отправка должна уметь делить текст на части безопасно.

## Какие паттерны используют другие приложения

### DailyBot

`Check-ins` строятся на структурированных prompt-ах и повторяемом async-ритме.
Сильная сторона подхода: не “свободное эссе”, а короткий check-in по понятным блокам.

Источник:
- `https://help.dailybot.com/hc/en-us/articles/25101121993107-Check-ins`

### Geekbot

Официальные материалы Geekbot вокруг standup-ов делают акцент на асинхронности, краткости и понятных вопросах.
Сильный паттерн: один update должен читаться быстро и не требовать расшифровки.

Источники:
- `https://www.geekbot.com/blog/daily-standup-meetings`
- `https://help.geekbot.com/en/articles/875402-how-geekbot-works`

### Fellow

В официальных материалах Fellow standup подаётся как короткий ритуал с упором на ясность, блокеры и follow-up.
Сильный паттерн: standup не должен быть длинной статусной простынёй.

Источник:
- `https://fellow.app/blog/meetings/how-to-run-daily-standups-like-a-great-boss/`

## Что из этого внедрено

### В интерфейс

- короткие формулировки полей;
- helper chips с подсказкой “1-3 пункта / без длинных абзацев / один пункт = один факт”;
- onboarding без лишней теории;
- digest/preview и Telegram-text разделены.

### В отчёты

- длинные пункты сжимаются и дробятся на более короткие элементы;
- большие raw notes больше не должны рендериться как единственная стена текста;
- plain-text версия готовится отдельно.

### В Telegram flow

- HTML-отчёт преобразуется в plain text;
- длинные сообщения режутся на безопасные chunks.

## QA-кейсы для ручной проверки

### Авторизация

1. Открытие в Safari по прямой ссылке.
Ожидание: понятный экран, что Mini App надо открывать из Telegram.

2. Открытие из Telegram Mini App.
Ожидание: авторизация проходит автоматически, auth-экран не показывается.

### Onboarding

3. Первый вход пользователя.
Ожидание: onboarding короткий, помещается на мобильном экране без ощущения перегруза.

4. После подтверждения onboarding.
Ожидание: он скрывается и не мешает следующему запуску.

### Быстрый апдейт

5. Короткий структурированный апдейт.
Ожидание: заметка сохраняется, digest собирается без лишнего мусора.

6. Новый проект через форму.
Ожидание: проект создаётся автоматически и не падает в Inbox.

### Длинные заметки

7. Вставка длинной заметки с несколькими статусами и действиями.
Ожидание: preview остаётся коротким и читаемым.

8. Открытие “Показать исходный текст”.
Ожидание: полный текст доступен, но не мешает основному экрану.

### Digest / Telegram text

9. Сборка digest после нескольких заметок.
Ожидание: есть отдельный читаемый preview и отдельный plain-text блок.

10. Кнопка “Копировать текст”.
Ожидание: текст копируется без HTML.

11. Отправка длинного отчёта в Telegram.
Ожидание: текст отправляется частями и не падает из-за лимита длины.

### История и Inbox

12. Inbox с длинной note.
Ожидание: карточка не превращается в простыню.

13. История заметок.
Ожидание: каждая карточка показывает summary, а не только raw dump.
